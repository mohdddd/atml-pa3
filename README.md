# ATML PA3 — Fine-Tuning, Visual Grounding, and Test-Time Compute

Code, configurations, split/example IDs, environment specification and machine-readable results for
Programming Assignment 3 of EE-5102/CS-6304 *Advanced Topics in Machine Learning* (Fall 2026).

| Task | Topic | Status |
|---|---|---|
| 1 | LLM fine-tuning of Qwen3-0.6B on MetaMathQA: Full FT, Full FT + L2-SP, LoRA-4, LoRA-16, OPLoRA-16 | complete |
| 2 | SigLIP → MLP connector → Qwen3-0.6B VLM, 3-stage curriculum, grounding with complementary pairs | complete |
| 3 | Test-time compute: Best-of-N, self-consistency, self-certainty, VisConf/RWC, refinement, adaptive sampling | complete (offline steps on CPU; Step 4 on one Kaggle T4, 2.0 h, 15–16 Nov) |

All experiments run on **Kaggle, 2× NVIDIA T4 (16 GB, no BF16)**, hence FP16 autocast with dynamic loss
scaling everywhere. Global seed **6304**.

Not committed: raw datasets, model weights and recovery checkpoints. Checkpoints are backed up to a
private Hugging Face Hub repo (`pa3/common/hub.py`); every number in the report traces to a file in
`results/` produced by a command listed below.

## Running on Kaggle

1. Notebook settings: **Accelerator → GPU T4 x2**, **Internet → On**.
2. **Add-ons → Secrets**: attach `GH_TOKEN` (fine-grained GitHub PAT, *Contents: read & write* on this
   repo only) and `HF_TOKEN` (Hugging Face, write scope) to the notebook.
3. The first cell of every notebook in `kaggle/` is the same bootstrap: it reads the secrets, writes a git
   credential file, clones this repo to `/tmp`, and installs requirements. Results are pushed back with
   `pa3.common.gitsync.push`. Long runs are executed with **Save Version → Save & Run All (Commit)**.

### Task 1 — LLM fine-tuning

Everything (5 training runs, 7 evaluation conditions, diagnostics, qualitative generations, summary
tables/figures) runs unattended in one Kaggle session with two T4s:

1. `kaggle/10_task1_check.ipynb` (interactive, ~20 min): the full pipeline in miniature
   (`PA3_DRY_RUN=1`: 3 updates per method, 16 examples per benchmark) → `results/task1_dryrun/`.
2. `kaggle/11_task1_full.ipynb` (**Save & Run All**): `python -m pa3.task1.pipeline run`.
   If the session ends early, rerun it: finished jobs are skipped and interrupted training resumes from
   its newest recovery checkpoint.

| Step | Command | Output |
|---|---|---|
| data selection, probe set | `python -m pa3.task1.pipeline prepare` | `splits/task1/metamath_selection.json`, `splits/task1/probe_set.json` |
| one training run | `python -m pa3.task1.train --run {full_ft,l2sp,lora4,lora16,oplora16}` | `results/task1/<run>/` (config, `train_log.jsonl`, `resources.json`, `merge_check.json`) |
| one evaluation condition | `python -m pa3.task1.evaluate --cond {baseline,full_ft_mid,full_ft,l2sp,lora4,lora16,oplora16}` | `results/task1/eval/<cond>/` (metrics, per-example outputs, qualitative, diagnostics) |
| tables and figures | `python -m pa3.task1.aggregate` | `results/task1/summary/`, `figures/task1/` |

Settings: `configs/task1/task1.yaml`. Implementation notes:
* Data: first 40,000 eligible MetaMathQA examples in source order (empty, >2,048 formatted tokens, or
  query/original question matching a GSM8K test question after normalisation are excluded); Qwen3 chat
  template with `enable_thinking=False`; loss on response tokens + `<|im_end|>`, normalised by the number of
  supervised tokens in the 32-example effective batch.
* Precision: FP16 autocast + dynamic loss scaling; FP32 master weights (full FT) or frozen FP16 backbone
  with FP32 adapters (LoRA/OPLoRA); FP32 AdamW states. The LM head and cross-entropy are applied only to
  supervised positions in checkpointed chunks (`pa3/task1/modeling.py:sft_loss_sum`); this is
  mathematically the standard loss and only avoids materialising full-vocabulary FP32 logits.
* L2-SP: Ω = ½‖θ − θ₀‖² over all unique parameters; θ₀ is kept in pinned CPU memory and streamed to the
  GPU every update, and λ(θ − θ₀) is added to the unscaled gradient before clipping.
* LoRA/OPLoRA: one implementation (`pa3/task1/lora.py`); OPLoRA projects the factors with the frozen
  top-128 singular bases of each W₀ (FP32 SVD) and exports the projected factors, which are merged into a
  fresh FP16 backbone for evaluation (merged-vs-unmerged logits are checked after training).
* Evaluation: lm-evaluation-harness 0.4.13 — `gsm8k_cot` 0-shot with the non-thinking chat template,
  greedy, 1,024 new tokens (flexible-extract EM primary); HellaSwag / BoolQ / ARC-Easy log-likelihood
  without chat template. A GSM8K response is flagged truncated when its re-tokenised length is within one
  token of the cap.
* Weight/activation diagnostics use `mlp.down_proj` of layers 0/13/27 in FP32 with probe inputs cached from
  the starting model.

### Task 2 — VLM and visual grounding

SigLIP-base (frozen, 196 × 768 patch features cached once in FP16) → MLP connector (Linear 768→1024, GELU,
Linear 1024→1024) → Qwen3-0.6B (frozen FP16; LoRA r 16 / α 32 / dropout 0.05 on q/k/v/o in stages 2–3),
trained through a 3-stage curriculum (caption alignment 2,250 updates → visual instruction tuning 1,500 →
natural VQA 750), then evaluated for grounding with complementary pairs and image controls. The optional
49-token run (2×2 average pooling of the 14×14 grid before the connector) trains in parallel on the second
GPU with the same seed, data, budgets and evaluation.

1. `kaggle/20_task2_check.ipynb` (interactive, ~20–30 min): the whole pipeline in miniature
   (`PA3_DRY_RUN=1`: 6 + 4 + 4 updates, small training subsets, full evaluation sets) → `results/task2_dryrun/`.
2. `kaggle/21_task2_full.ipynb` (**Save & Run All**): `python -m pa3.task2.pipeline run`. Rerunning skips
   finished jobs and resumes interrupted training from its newest checkpoint (every 250 updates).

| Step | Command | Output |
|---|---|---|
| data selection (run once, committed) | `python -m pa3.task2.data select` | `splits/task2/{captions,grounding,vqa,mismatched}.json`, `selection_summary.json` |
| images + label audit | `python -m pa3.task2.pipeline prepare` | `results/task2/images.json`, `figures/task2/label_audit_grounding_test.png` |
| SigLIP feature cache | `python -m pa3.task2.pipeline cache` | `results/task2/feature_cache.json`, `feature_checks.json` |
| curriculum training | `python -m pa3.task2.train --variant {t196,t49}` | `results/task2/<variant>/` (config, `train_log.jsonl`, `dev_log.jsonl`, `dev_examples.jsonl.gz`, `checks.json`, `calibration.json`, `resources.json`) |
| final evaluation | `python -m pa3.task2.evaluate --variant {t196,t49}` | `results/task2/<variant>/eval/` (`metrics.json`, `test_examples.jsonl.gz`) |
| tables and figures | `python -m pa3.task2.aggregate` | `results/task2/summary/`, `figures/task2/` |

Settings: `configs/task2/task2.yaml`. Implementation notes and choices the assignment leaves open:
* **Data** (seed 6304; train2014 for training, val2014 for development / final test; all 528 evaluation
  images are distinct and disjoint from training — `selection_summary.json → isolation`).
  Captions: 6,000 train images × 3 captions (18,000 examples), 96 dev images × 1 caption; captions over the
  64-token cap are never chosen. Grounding: presence pairs (“Does this image contain a/an *object*?”: an image
  whose largest non-crowd instance of the category covers ≥ 1% of the image vs. an annotated image with no
  annotation of that category) and counting pairs (“How many *objects* can you see?”: two images with different
  counts in 1–4, all instances non-crowd and ≥ 0.5% of the image; broccoli and skis excluded as not countable).
  Category uniform, then images; counts uniform among available values. Reusable training pools of 3,000
  presence + 2,000 counting pairs; dev 12 + 12 pairs, final test 32 + 32 pairs. VQAv2: complementary pairs
  with identical question text and answer type, differing normalised consensus answers, ≥ 8/10 agreement on
  each image, question ≤ 80 and answer ≤ 16 tokens; target = most frequent original string of the consensus
  group; train 640/256/640, dev 12/8/12, test 36/24/36 (yes/no / number / other).
* **Answer normalisation / scoring**: port of the official VQA evaluation normalisation, applied to every
  string (`pa3/task2/vqa_norm.py`); grounding = normalised exact match; VQAv2 = local soft consensus accuracy
  over all ten answers.
* **Prompt**: user turn = `<visual tokens>\n<text>` in Qwen3’s chat template with `enable_thinking=False`;
  questions get the suffix “Answer the question using a single word or phrase.”, captions use the instruction
  “Write a short caption for this image.”. No-image inputs drop the visual tokens and their `\n` (prompt
  shorter by 197 tokens; masks and positions rebuilt).
* **Connector calibration** (training data only): the connector output is multiplied by a fixed,
  non-trainable scalar chosen once at initialisation so that the mean L2 norm of visual tokens equals the mean
  norm of Qwen input embeddings of training text tokens (`calibration.json`). Keeping the scalar outside the
  weights leaves the MLP at its standard initialisation (folding the ~0.05 factor into the weights made
  AdamW's 1e-3 steps change them by ~60% per update in a test run).
* **Optimisation**: fresh AdamW per stage (weight decay 0.01, biases excluded), warmup ceil(5%) of the stage
  (113 / 75 / 38 updates) then cosine to 10% of the stage peak; loss = per-example mean over answer/caption
  tokens + `<|im_end|>`, averaged over the 16-example effective batch. Stage 2–3 draws are sampled i.i.d.
  from the stage mixture with a seeded sampler; pool items in seeded shuffled cycles.
* **Evaluation**: greedy, 16 new tokens, batch 8, four image conditions (correct / complementary swap /
  fixed mismatched mapping / no image); 95% CIs from 4,000 pair-bootstrap resamples with matched pair IDs
  for differences. Because both questions of a pair have the same wording, the complementary-swap input for
  one question is the correct-image input of the other (the swap predictions are still generated separately).
* **Known gap in the logs**: `results/task2/t196/train_log.jsonl` lacks the row of update 2,250 (4,499 of
  4,500 rows). The old result-push helper ran `git pull --rebase --autostash` in the shared working tree while
  the other GPU process was appending to its log, and the row written in that window was overwritten.
  Training, checkpoints, dev metrics and evaluation are unaffected; pushes now go through a separate
  worktree (`pa3/common/gitsync.py`).

### Task 3 — Test-time compute

Offline steps (1, 2, 3, 5, 6) run on CPU from the supplied rollouts (about 8 min, dominated by math-verify
grouping); Step 4 (live generation) runs on one Kaggle T4.

1. Get the supplied `ATML-PA3-Data` folder (Drive link in `kaggle/make_notebooks.py`, or `kaggle/01_fetch_task3_data.ipynb`);
   the file hashes are in `splits/task3/data_manifest.json`. Then
   `PA3_T3_DATA=/path/to/ATML-PA3-Data python -m pa3.task3.pipeline offline`.
   The released MathVista testmini metadata is downloaded once from `AI4Math/MathVista` at revision
   `2b6ad694…` (non-image columns only) and cached next to the data folder.
2. `kaggle/30_task3_check.ipynb` (interactive, ~5–10 min, `PA3_DRY_RUN=1`: 2 questions, tiny caps →
   `results/task3_dryrun/`), then `kaggle/31_task3_full.ipynb` (**Save & Run All**):
   `python -m pa3.task3.pipeline live`. Each call is appended to `results/task3/live/calls.jsonl` and pushed
   every 5 questions; a rerun skips finished calls. Afterwards run `python -m pa3.task3.aggregate` to add the
   live table/figure to the summary.

| Step | Command | Output |
|---|---|---|
| splits, orders, answer labels (scorer fixed here) | `python -m pa3.task3.prepare` | `splits/task3/{splits.json,orders.json.gz,live_questions.json}`, `results/task3/answers/` (`<ds>_rollouts.parquet`, `<ds>_groups.jsonl.gz`, `scorer.json`), `results/task3/data_checks.json` |

| Step 5: adaptive stopping | `python -m pa3.task3.adaptive` | `results/task3/adaptive/` (`<ds>_dev_grid.csv`, `<ds>_selected.json` (frozen), `<ds>_eval_selected.csv`, `<ds>_eval_*_runs.parquet`, `<ds>_stopping_relations.csv`, `<ds>_vs_fixed_budget.csv`, `<ds>_eval_grid_retrospective.csv`) |

| unit tests | `python -m pytest tests/test_task3_core.py -q` | tie rules, average-rank RWC, margin, prefix-only VisConf calibration, covariance identity, answer normalisation |

Settings: `configs/task3/task3.yaml`. Implementation notes and the choices the assignment leaves open:
* **Data / join**: the three parquet files are joined on `(dataset, sample_id, rollout_id)`; every per-token list
  (logp, kl_u_p, the three attention groups) has the length of `generated_token_ids` = `n_generated_text_tokens`,
  attention’s preceding-token counts are 0…T−1, and the totals match the data README (20,742,094 / 8,961,703
  tokens, 523 / 487 capped, 521 / 3,032 null extractions) — `results/task3/data_checks.json`. No rollout has
  zero tokens.
* **Splits**: within each dataset, sorted IDs permuted by `np.random.default_rng(6304)`; first 200 = dev, rest
  = held-out; live subset = first 50 MATH held-out IDs. **Orders**: 10 permutations of the 32 rollout IDs per
  question from `default_rng([6304, d])` (d = 0 MATH, 1 MathVista), questions in sorted-ID order; the
  candidate set for budget N is the first N of an order, reused by every method and stopping policy.
* **Answers / scorer** (`pa3/task3/answers.py`, version `pa3-task3-scorer-1`, math-verify 0.9.0, fixed before
  any evaluation, labels in `results/task3/answers/`). Missing extractions → one `NO_ANSWER` group (always
  incorrect, kept in voting, cost and accuracy).
  *MATH*: groups formed without gold — distinct answer strings are visited in order of first rollout ID and join
  the first group whose representative is equivalent (`verify(parse(rep), parse(s))`, answers wrapped as
  `\boxed{…}`; unparsable strings match only by exact string). Groups are graded with the same rule against the
  gold answer; each rollout inherits its group’s label (0 disagreements with grading each rollout’s own string).
  43 comparisons involving answers with towers of exponents (e.g. `(…)^{(3^{101}-3)/2}`) hit math-verify’s 5 s timeout; a timeout counts as
  “not equivalent” and every such pair is listed in `scorer.json`.
  *MathVista*: the official `normalize_extracted_answer` rules with the released metadata — multiple choice:
  “(X)” → X, option letters kept, exact option text → its letter, otherwise the most similar option by
  Levenshtein distance (first on ties); answers represented as letters (the supplied gold letters match the
  metadata for all 1,000 questions); integer `str(int(float(x)))`, float `str(round(float(x), precision))`,
  list `str(list)`. Because the supplied extractor keeps LaTeX, free-form answers first pass a conservative
  cleaner (`\frac{a}{b}`, `\%`, `^\circ`, `\text{…}`/`\mathrm{…}` units, thousands commas, `a\times10^k`,
  one trailing plain unit word). Extractions that are still not numbers of the required type (e.g.
  “10-15 years” for an integer answer; 1,013 rollouts) keep their own always-incorrect group keyed by the raw
  string rather than being merged into NO_ANSWER.
* **Methods** (`pa3/task3/offline.py`, `selection.py`): FirstAns, self-consistency, highest mean log-prob,
  highest self-certainty, self-certainty + RWC (both datasets); vision-only and VisConf, each highest-score and
  RWC (MathVista). Also computed: mean log-prob + RWC (the remaining cell of the score × aggregation grid),
  shortest-rollout selection (length-only control) and tokenwise fusion Z_token (highest and RWC) at every N.
  VisConf calibration uses the 5th/95th linear-interpolation percentiles of the token KL values pooled over the
  current candidate set only, recomputed for every prefix. Ties: earliest supporting rollout in the current
  order (highest score and votes; vote totals within 1e-9 count as tied); average ranks for tied RWC scores;
  N = 1 returns the only candidate. Token cost = sum of retained token counts of consumed candidates (FirstAns:
  its first only).
* **Reporting**: headline numbers use the 800 held-out questions (dev reported alongside in every CSV);
  outcomes are averaged over the 10 orders within a question, then across questions. 95% intervals: 1,000 paired
  question-level bootstrap resamples (seed 6304) of the order-averaged per-question accuracies, for each method
  vs self-consistency, RWC vs highest for each score, VisConf vs self-certainty, VisConf vs vision-only and
  tokenwise vs trajectory-level fusion, at every N ≥ 2 (`bootstrap_diffs.csv`).
* **Step 3** (`signals.py`, N = 32): Spearman(length, score) per question; Pearson(score, correct) per question
  with mixed correctness; top-minus-bottom quartile correctness = 8 highest vs 8 lowest of 32 (ties broken by
  rollout ID), averaged over all questions and over mixed questions (bootstrap CI over questions).
  Confidence–vision: Pearson(c_t, v_t) within each rollout with c calibrated on the question’s full pool,
  summarised by question means. The identity Z_token − Z = Cov_t(c, v) holds to 1.3e-14.
  Trajectories: held-out questions in split order, the first 3 with 8–24 correct rollouts; in each, the correct
  and the incorrect rollout with the highest quality score (Z for MathVista, K for MATH).
* **Step 5** (`adaptive.py`): checks after 4, 8, 16 revealed rollouts, else 32; both controllers return the current
  self-consistency answer. Agreement: unique SC leader (no tie for the top count), not NO_ANSWER, count ≥ τ·n.
  Quality-aware: additionally the SC and RWC winners agree and the RWC margin (largest − second-largest vote
  over total weight; 0 runner-up if one group) ≥ γ, with self-certainty (MATH) or VisConf (MathVista) recomputed
  on the revealed rollouts. Selection on dev only (lowest mean cost within 1 pp of fixed-32 SC; ties: higher
  accuracy, smaller τ, smaller γ; always-32 fallback in each family), written to `<ds>_selected.json` before the
  held-out run. Early-stop analyses count (question, order) runs. The held-out grid is saved only as a
  retrospective accuracy–cost frontier.
* **Step 4** (`live.py`): Qwen/Qwen2.5-3B-Instruct @ `aa8e7253…`, FP16, batch 1, temperature 0.7, top-p 0.8,
  top-k 20, repetition penalty 1.0 (passed explicitly; the model’s generation config default is 1.05), chat
  template with system “You are a helpful assistant.” and `problem + "\n\n" + instruction` (as in the data
  README). Seeds: `6304·1000 + 10·question_position + call_index` (0 single, 1–3 parallel, 4 revision); calls
  run question by question on `cuda:0` after one untimed warm-up. Time per call = tokenisation + generation +
  decoding (CUDA-synchronised), excluding model loading; peak memory = `max_memory_allocated` per call. Output
  tokens exclude the stop token; a call is truncated if it hit its cap without a stop token. Parallel: self-
  consistency over the three answers with the same grouping/tie rules. Refinement reuses parallel response 1 as
  the initial response; the revised answer is the last box of the revision response (none → NO_ANSWER); its
  cost includes the initial response, the longer revision prompt and all revision output.
